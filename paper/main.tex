\begin{abstract}
Continuous integration turns a security property into a green check, and a green
check is easily mistaken for a guarantee. We report a reproducible \emph{case study}
in \emph{testing} that green check for one secure multi-party computation (MPC)
application: the deterministic-query fragment of the knowledge-threshold belief
computation of Mardziel, Hicks, Katz and Srivatsa (PLAS 2012), implemented on
MP-SPDZ with three-party replicated secret sharing. The subject has no ground-truth
oracle, so we build a separately implemented plaintext \emph{pseudo-oracle}, an
\emph{anti-echo} interface that keeps expected outputs out of the system under test,
a strict runtime transcript check, and recomputed, hash-bound test evidence; a
bounded 228-case adversarial matrix and five committed executable negative controls
exercise a static \emph{delivery-conformance} checker that inspects compiled
assembly. We evaluate that checker's adequacy by \emph{mutation analysis} under a
build-time fault model, and---because an adaptive mutation sequence overfits the
tool it hardens---we add a \emph{pre-registered, out-of-sample held-out mutation
study}: 22 mutants with predictions committed \emph{before} execution and run once
against the frozen checker. The decisive result is a \emph{surviving,
source-realizable} mutant, H-R2: a multiset-preserving mis-delivery that the
structural checker accepts and that only a downstream transcript oracle catches, for
that concrete mutant. We report exact-strength results and honest mutant accounting
(killed / survived / stillborn), and we deliberately avoid an aggregate mutation
score for manifest-level probes whose source realizability is unproven. The whole
study reproduces from a fresh checkout, and the compiled-assembly signatures
reproduce on the pinned backend and one additional MP-SPDZ version. We do not claim a
new analysis technique or a privacy proof; the contribution is a conformance-testing
and mutation-adequacy methodology, applied and reproduced, and an honest map of what
it establishes and where it stops.
\end{abstract}

\section{Introduction}
\label{sec:intro}
An MPC framework such as MP-SPDZ~\cite{keller2020mpspdz} compiles a program into a
protocol that several parties execute so each learns only its prescribed output.
Building a correct \emph{application} on top of such a framework is a separate task
from the framework's own security argument: an application author can, by accident or
by an injected fault, write source that reveals a value the functionality was meant to
protect. When such an application is wired into continuous integration (CI), a passing
test suite is easy to mistake for evidence that the privacy property holds. This paper
is a case study of \emph{what that test suite can and cannot establish}, told in the
vocabulary of software testing: test oracles, conformance tests, and mutation
adequacy.

We are explicit about what this paper is \emph{not}. It is not ``the first
implementation of PLAS belief tracking,'' and makes no such claim. It is not a new
program-analysis \emph{technique}: the observation that information-flow safety depends
on dataflow and semantics rather than instruction names is prior art
(\S\ref{sec:related}). We frame the work as a \emph{testing case study / experience
report} whose value is (i) a concrete conformance-test design for a subject with no
ground-truth oracle, (ii) a \emph{pre-registered, held-out} mutation study of a
static conformance checker, and (iii) an honest, reproducible account of test
adequacy---including a surviving mutant that reveals a real fault the checker misses.

\paragraph{The testing problem}
The subject computes, per recipient, whether releasing a query's output would let a
protected party's posterior belief exceed a public threshold, and---on accept---delivers
the output \emph{privately} to only the intended recipient. Two properties must be
tested: functional correctness of the accept/reject/mask decision, and the
\emph{delivery} discipline (only party $j$ learns $(\text{accept}_j,
\text{payload}_j)$). There is no reference implementation to serve as an oracle, and
the naive way to obtain one---feeding expected outputs into the harness---risks the
classic \emph{oracle-in-the-SUT} anti-pattern, where the test passes because the
expected answer leaked into the system under test.

\paragraph{Contributions (all testing, no new research)}
\begin{enumerate}[leftmargin=1.4em,itemsep=2pt]
\item A \textbf{conformance-test design} for a privacy-critical MPC application
(\S\ref{sec:method}): a separately implemented plaintext \emph{pseudo-oracle}, an
\emph{anti-echo} interface that keeps expected outputs and post-state out of the
system under test, a strict runtime transcript check that fails closed on the
enumerated cases, and recomputed, hash-bound test evidence.
\item A \textbf{reproducible test artifact} (\S\ref{sec:results}): a fixture, a bounded
228-case adversarial matrix checked against the pseudo-oracle, and five committed
executable negative controls, run against a pinned backend.
\item A \textbf{mutation analysis} of a static delivery-conformance checker
(\S\ref{sec:mutation}), with honest \emph{killed / survived / stillborn} accounting,
and---to counter the overfitting inherent in an adaptive mutation sequence---a
\textbf{pre-registered, out-of-sample held-out mutation study} (\S\ref{sec:heldout})
whose decisive result is a \emph{surviving} source-realizable mutant (H-R2).
\item A statement of \textbf{test adequacy and its boundary} (\S\ref{sec:boundary}):
what the layered checks establish operationally, and the two verification obligations a
privacy \emph{guarantee} would additionally need.
\end{enumerate}
We also report the reproduction of the whole study from a fresh checkout and a
cross-version replication of the backend-level test observations (\S\ref{sec:repro}).
Every number, mutant, and result below is unchanged from a frozen artifact baseline;
this paper re-frames and re-packages that testing evidence.

\section{Subject and Fault Models}
\label{sec:background}

\paragraph{The subject under test (deterministic-query fragment)}
Following PLAS 2012~\cite{plas2012}, $N$ parties hold secrets in a finite domain $D$;
each observer $j$ holds a belief over the others' secrets. For a query $Q$, the
mechanism checks, per recipient, whether releasing $Q$'s output would let any protected
party's posterior exceed a public threshold, quantifying over \emph{every possible
output} so the accept/reject decision is simulatable; on accept the recipient privately
learns the output, on reject a masked constant, and no party may learn another's
verdict. We test deterministic, total, public queries; two instantiate the subject:
\code{p1\_is\_max} and \code{sum\_even}.

\paragraph{Backend}
Circuits are compiled and run with MP-SPDZ pinned at \code{9d809599}, backend
\code{replicated-ring-party.x}: three-party replicated secret sharing over $\Ztfour$,
semi-honest, honest majority. The compiler emits a manifest of \emph{tapes} (a main
tape plus comparison subtapes). Two backend facts recur and matter for the checker
under test. First, a public reveal and a legitimate masked comparison-open are the
\emph{same} opcode: MP-SPDZ ``uses a single instruction for
opening''~\cite{keller2020mpspdz}, and the correctness-check flag does not change this.
Second, a value in one tape reaches another only through memory or through register
arguments passed by \calltape{} (opcode \code{0xec}) and received by \callarg{} (opcode
\code{0xed}); a direct cross-tape register reference is a compiler error.

\paragraph{Two fault models}
We keep two fault models distinct throughout; conflating them is what makes the
mutation study sound either vacuous or over-strong.

\begin{description}[leftmargin=1em,itemsep=2pt]
\item[Runtime protocol fault model.] At most one semi-honest corrupted party among the
three; honest majority; authenticated encrypted channels; process isolation (stated,
\emph{not} enforced by the single-host test harness). This is the model a
\emph{protocol-level} privacy argument would target. Our functional and conformance
tests do \emph{not} address it; that hand-off is \S\ref{sec:boundary}.
\item[Build-time mutation fault model.] Faults are injected into the application
\code{.mpc} source \emph{and only there}. The pseudo-oracle, the checker, the policy
(thresholds, expected delivery), the CI workflow, the evidence validator, and the
\emph{pinned} MP-SPDZ compiler are the \emph{trusted test infrastructure} and are
\emph{not} mutated. This is the operator space of the mutation analysis
(\S\ref{sec:mutation}). Were the test infrastructure itself faulty, every automated
check would be trivially void; stating the model is what makes the mutant accounting
meaningful.
\end{description}
Fig.~\ref{fig:arch} draws the boundary. We make no claim under collusion, a malicious
party, unencrypted channels, or a shared host, and no performance claim.

\section{Conformance-Test Design}
\label{sec:method}

Each element exists to defeat a specific way a conformance test can be vacuous. We
state what each element \emph{operationally} provides, not that it is ``sound.''

\paragraph{A separately implemented pseudo-oracle}
The test oracle is a plaintext model written from the paper, separately from the
circuit and from the project's earlier exact-rational reference model, transcribing the
all-possible-outputs check directly. It is a \emph{pseudo-oracle}~\cite{oracleproblem}
(a separate implementation of the same specification), \emph{not} an independently
validated ground truth: it shares the specification with the circuit, so a
\emph{correlated} misreading of PLAS could make both agree on the wrong behaviour. It
did carry one fatal transcription error (conditioning on the actual output only) until
testing caught it. We state this shared-specification / correlated-error risk wherever
we rely on oracle agreement (\S\ref{sec:threats}). This is the pseudo-oracle instance
of the general oracle problem~\cite{oracleproblem}, and is close in spirit to
metamorphic testing~\cite{metamorphic} in that it substitutes a derivable relation for
an unavailable ground truth.

\paragraph{An anti-echo interface (avoiding the oracle-in-the-SUT anti-pattern)}
Before any circuit was written, the interface was fixed so that expected outputs and
expected post-state \emph{never enter the system under test}---neither compiled in nor
supplied as runtime inputs; they live only in the external harness, obtained from the
pseudo-oracle. Circuit inputs are exactly the public parameters and the secret-shared
secrets and beliefs, and the harness runs at least one state beyond the fixture, so a
constant-output circuit cannot pass by accident. Beliefs travel as dense unnormalized
non-negative integer weights; the threshold check avoids division ($b\,M \le a\,Z$).
Because MP-SPDZ comparison is signed, the no-wraparound requirement is $B < 2^{k-1}$
(not the naive $2^k > B$), which we pin with a counterexample test.

\paragraph{A strict transcript oracle}
A correct party's captured stdout must be exactly its two own records; any foreign,
duplicate, unknown, missing, or extra line makes the test \emph{fail
closed}. This is an operational output-conformance oracle over the enumerated
transcript cases on the observed stdout channel; it observes selected output channels
and does not establish absence of every possible leak. It becomes the second line of
defence in \S\ref{sec:heldout}.

\paragraph{Recomputed, hash-bound test evidence}
Each run retains a typed record; in CI the validator requires each record's source hash
and delivery signature to equal values recomputed from the checked-out source and a
fresh compile, and binds each record to a canonical case via a recomputed input hash and
pseudo-oracle verdict. This establishes \emph{self-consistency and provenance} of the
test evidence \emph{under the trusted CI workflow}; it is not integrity against an actor
who can alter source, checker, workflow, and evidence together (outside the fault model
of \S\ref{sec:background}). It is the evidence-discipline neighbour of reproducible
builds~\cite{reprobuilds}, recomputed per test case rather than attesting a whole
artifact.

\subsection{Test artifact and results}
\label{sec:results}
On the fixture (two invocations: one all-accept, one with a per-recipient reject and
belief preservation) plus two further valid states, the circuit reproduces the
pseudo-oracle's visible outputs, payloads, and reconstructed weights. A \emph{bounded,
constructed} adversarial matrix of 228 cases (216 single-invocation $+$ 12 carried; all
27 secret tuples $\times$ two queries $\times$ uniform / non-uniform / per-party-scaled
integer weights near the bit bound) all match the pseudo-oracle. This is a constructed
test matrix, \emph{not} general coverage. The conformance package holds 92 collected
tests---46 functional and 46 delivery-checker tests---and 9 reference test functions
(25 collected items), all green; \emph{test counts are not themselves a result}. Five
committed executable negative controls are rejected by the checker (\S\ref{sec:mutation}).
No timing is reported.

\section{Mutation Analysis of the Delivery Checker}
\label{sec:mutation}

Functional conformance says nothing about \emph{how} a value is delivered: a circuit
can compute correct verdicts and broadcast them. We therefore built a static
delivery-conformance checker that inspects the compiled tape manifest, and evaluated
its \emph{adequacy} by mutation analysis under the build-time fault
model~\cite{demillo1978,jiaharman}. We are explicit that the first sequence is
\emph{retrospective and adaptively discovered}, not a complete or independently designed
operator set: the checker was repeatedly hardened against the same mutants later used as
evidence (adaptive overfitting), so this sequence yields no held-out adequacy estimate.
We remove that threat in \S\ref{sec:heldout}.

\paragraph{Mutant accounting}
One motivating transcript failure (\textbf{B0}); six compiled-delivery mutants
(\textbf{B1--B6}); one semantic mutant (\textbf{S1}). The six are not homogeneous: B1,
B2, B3 and B5 are committed executable \emph{source} mutants; \textbf{B4 is a synthetic
compiled-manifest counterexample, not a source \code{.mpc}}; and B6 is a reconstructed
source mutant whose naive realization is itself \emph{killed} (\S\ref{sec:b6}). B0:
changing \code{reveal\_to(j)} to a public \code{reveal()} while keeping the per-party
print compiles to a public open of every verdict, yet a stdout-only test reported
success---which motivated inspecting the \emph{compiled} delivery. B1--B3 and B5 each
\emph{survived} the then-current checker \emph{as committed source mutants} and were
killed by adding a detection rule (separate-tape reveal; name-spoofed subtape;
\code{reveal(False)}---still a public open; and the vectorized-memory variant).
\textbf{B4} is different: it is the observation that the multiset rule is blind to tape
\emph{bodies}---a \code{reveal(False)} of the verdict placed in an \emph{existing}
\code{EQZ(3)\_63} body with the three pinned names intact---demonstrated with a
\emph{synthetic manifest}, not a compiled source mutant; against the final checker it is
killed by the subtape-memory rule (the multiset left intact). The clean build stores
nothing in its main tape and touches no memory in its subtapes, so forbidding memory is
a restriction with no false positives on the honest build.

\subsection{B6, at its exact strength}
\label{sec:b6}
We scope B6 precisely, because it is easy to overstate. We reconstructed a mutant that
routes party~1's verdict through the \calltape/\callarg{} register channel (a
\code{@function\_tape} that receives the verdict as a register argument and opens it).
Compiled against the pinned backend and checked by the final checker, this mutant is
\textbf{KILLED}: the added tape breaks the pinned comparison-subtape multiset, and
MP-SPDZ's call frame also spills through memory, tripping the memory rules. So
\textbf{B6 is not a demonstrated bypass of the final checker}; because a direct
cross-tape register reference is a compile error, the B3/B5 source mutants therefore
used an attacker-introduced memory hop, which the memory rules catch.

Its content is narrower and precise. The \emph{honest} build passes secret comparison
operands across the tape boundary via \calltape{} (in main) received by \callarg{} in
each of the three comparison subtapes---no memory. Therefore a detection rule that
forbade cross-tape register-argument transfer of secrets, the way the memory rules close
the memory channel, would \textbf{reject the honest build}: the \callarg{} channel
\emph{cannot be blocklisted by opcode/channel identity} without a false positive on the
honest build. Combined with the opcode-identity fact (a masked open and a raw reveal are
the same instruction), the testing lesson is precise: \textbf{this opcode-identity /
channel-blocklist checker cannot be promoted to a general non-leakage checker}.
Distinguishing legitimate from leaking flows requires analysis stronger than
opcode/channel identity---operand/provenance-sensitive dataflow, typing, a verified IR,
or other semantic machinery---\emph{which we did not evaluate} (\S\ref{sec:related}).

\subsection{S1: a semantic mutant the checker cannot see}
\label{sec:s1}
On a different axis, a mutant that drops the reject-mask (delivers the true output even
to rejected recipients) \textbf{survives} every delivery-checker rule---the delivery
structure is intact---yet is \textbf{killed by the pseudo-oracle}: on
$\text{secrets}=(0,0,0)$, \code{p1\_is\_max}, the true output is $1$ and all parties
reject (oracle payload $0$), but S1 delivers $1$ to all three. We ran this
\textbf{end-to-end at the pinned backend}: all three parties complete (return code $0$)
and each delivers \code{ACCEPT 0 / PAYLOAD 1}, an executed oracle mismatch at parties
$[0,1,2]$ (raw evidence archived). This run is a \emph{functional} check only; it makes
no runtime, channel-security, or performance claim, and says nothing about the runtime
protocol fault model. Delivery-conformance checks \emph{how} values are delivered, not
\emph{which}; only the functional pseudo-oracle, bounded by test coverage, constrains
that.

\section{A Pre-Registered, Held-Out Mutation Study}
\label{sec:heldout}
The sequence above is adaptive and cannot estimate adequacy on unseen faults
(\S\ref{sec:threats}). Mutation analysis is only as credible as its independence from
the tool it evaluates, so we added a \emph{pre-registered, out-of-sample} study: a
corpus of 22 mutants with locked predictions was committed \emph{before} execution
(pre-registration) and run once against the frozen checker. It is out-of-sample but
\emph{not} an independent-adversary evaluation---the mutants and predictions were
authored within the same project that built the checker---so we report per-category
outcomes and \emph{no} aggregate mutation score.

\subsection{Mutation operators and the pre-registration protocol}
\label{sec:protocol}
The 22 held-out mutants instantiate seven operator categories, drawn from three sources
so the corpus is not a renaming of B0--B6: security mutation-testing practice
(systematic operator families, and separating \emph{stillborn} and \emph{equivalent}
mutants from killed ones~\cite{jiaharman,just2014}); the information-flow observation
that leakage is a dataflow rather than opcode-identity property, which \emph{predicts}
surviving value-routed and permutation mutants (\S\ref{sec:related}); and MP-SPDZ
backend mechanisms (the open family, the \calltape/\callarg{} register channel, memory
forms, sink opcodes, and the cross-tape compile error). The categories are: (1)
recipient/destination; (2) public/private open; (3) subtape/topology; (4)
secret-transfer/channel; (5) output/value-semantic; (6) transcript/output-channel; and
(7) evidence/provenance (which targets the \emph{separate} evidence validator, not the
delivery checker).

The protocol is two-phase and its integrity is visible in the commit history. First,
the corpus, the mutant sources or synthetic transforms, and a \emph{locked prediction}
for every mutant---predicted compile outcome, predicted checker verdict, source
realizability, and denominator membership---are committed \emph{before} the checker is
run on them. Second, the study is executed \emph{once} and the machine-readable results
are committed separately. We then classify each mutant honestly: \emph{killed} (checker
rejects), \emph{survived} (checker accepts), \emph{stillborn} (does not compile; never
counted as a kill), and \emph{benign/equivalent} (correctly not flagged). We record per
mutant whether it is \emph{source-realizable} (a compiled \code{.mpc}) or a
\emph{synthetic manifest-level probe} whose source realizability is unproven, and we
report \textbf{no aggregate mutation score over the synthetic probes}: a surviving probe
shows only that no rule fires on that assembly pattern, not that a source program can
produce it (B6 shows the naive realization is killed). All 22 outcomes matched their
pre-registered predictions---evidence about the checker's \emph{rules}, not about an
independent adversary's ingenuity (\S\ref{sec:threats}).

The decisive result concerns delivery \emph{structure}. Among three pre-registered
source-realizable recipient-structure mutants, the checker killed H-R1 and H-R3 and
\emph{survived} the multiset-preserving H-R2 permutation. \textbf{H-R2 is a demonstrated
source-realizable structural fault the checker misses}: a compiled build that delivers
each party's verdict to the \emph{wrong} recipient while preserving the pinned
destination-player multiset $[0,0,1,1,2,2]$---all that the main-tape delivery rule
inspects. It is killed only downstream: the strict transcript oracle
(\S\ref{sec:method}) rejected \emph{this concrete} build because a foreign
\code{PRIV\,$j$} record appears on the receiving party's stream; we do \emph{not} claim
the transcript oracle catches recipient permutations in general. Three source-realizable
\emph{semantic} mutants (negated accept, swapped accept/payload, a neighbour's payload)
likewise survive the checker and are killed by the pseudo-oracle, echoing S1. The
remaining \emph{synthetic} mutants are \emph{manifest-level rule-coverage probes}---
hand-built assembly patterns testing whether a rule fires, with \emph{unproven} source
realizability, \emph{not} executable mutants, and excluded from any mutation-score
denominator (the corpus also contains provenance and stillborn/compile-invalid cases,
scored separately). The informative probe is H-O3: a \callarg{} open of a
register-passed value in an existing masked subtape that no current rule rejects---the
same gap B6 names (\S\ref{sec:b6}), now exhibited at the manifest level. Table~\ref{tab:heldout}
summarizes the outcome classes.

\section{Reproduction and Cross-Version Replication}
\label{sec:repro}
The frozen artifact reproduces from a fresh checkout with a fresh build of the pinned
MP-SPDZ backend: 117 collected \code{pytest} items (the 92 conformance items plus the 9
reference test functions, which expand to 25), the named-case harness $4/4$, the
228-case matrix $228/228$, the recomputed evidence, and the B4/B6/S1 reproductions all
reproduce, and the normalized per-tape \code{manifest\_signature} values recompute to
the archived values. We reproduce those \emph{normalized-assembly} signatures,
\emph{not} raw binaries or assembly byte-for-byte. Separately, the backend-level test
observations replicate on one further MP-SPDZ version, v0.4.3 (\code{26a60536}): the
shared open-instruction family, the honest \calltape/\callarg{} path, the B6 behaviour,
and S1's structural survival with an executed oracle mismatch all recur, with no
compile/API or semantic change in what we exercised. This is two versions, not a
cross-version compatibility or version-independence claim: only one additional version,
on one host, for the probed observations, was tested. A one-command reproduction wrapper
and a machine-readable results file are in the artifact.

\section{What the Test Suite Establishes}
\label{sec:boundary}
Separating three levels keeps the claims honest.
\begin{enumerate}[leftmargin=1.4em,itemsep=1pt]
\item \textbf{General prior principle (not novel here):} information-flow safety depends
on dataflow and semantics, not opcode names---established for constant-time and
smart-contract bytecode (\S\ref{sec:related}).
\item \textbf{Case-study lesson (transferable, not empirically validated across
applications):} adaptive checking of a security property can produce false confidence,
and such tooling should print its adequacy boundary; ours does.
\item \textbf{Backend finding (backend-specific; observed at the pin \code{9d809599} and
one additional version, v0.4.3, not version-independent):} MP-SPDZ's shared open
instruction and the \calltape/\callarg{} path, and the consequence that the studied
opcode-identity / channel-blocklist checker cannot be promoted to a general non-leakage
checker.
\end{enumerate}

\paragraph{A layered account}
Concretely the assurance is a chain of partial checks, no one of them a privacy proof.
The pinned \emph{compiler} rejects one naive cross-tape transfer outright (a direct
cross-tape register reference is a compile error; the B3/B5 source mutants therefore
used an attacker-introduced memory hop). The \emph{delivery checker} kills gross
structural and channel mutant classes---public opens, illicit sinks, disallowed memory,
off-pin tapes---including forms outside its design set (exercised as manifest-level
probes, not executable source mutants), yet H-R2 shows it survives a multiset-preserving
wrong-recipient \emph{structure}. The \emph{transcript oracle} killed that one concrete
mutant; the \emph{pseudo-oracle} kills semantic mutants delivery-checking survives (S1
and the held-out semantic mutants); and \emph{evidence recomputation} protects the
consistency and provenance of these records under the trusted CI. In the tested
examples, later layers catch some faults earlier checks leave open; the layers are
complementary, not complete, and none, alone or together, is the protocol-level privacy
proof the hand-off below still requires.

\paragraph{What would make it a guarantee}
Two verification obligations, neither supplied by our tests: (i) \emph{privacy of the
executed circuit}---a Rep3 simulation argument or a formally-verified, dataflow-checked
comparison primitive; and (ii) \emph{semantic source-to-spec binding}---that the circuit
computes the intended function, not merely one that agrees with the pseudo-oracle on
tested cases (S1 shows why delivery privacy is insufficient without it). A Rep3 proof
establishes (i) and not (ii); our tests give coverage-bounded evidence toward (ii) and
nothing toward (i).

\section{Threats to Validity}
\label{sec:threats}
\begin{itemize}[leftmargin=1.2em,itemsep=1pt]
\item \textbf{Construct validity (test infrastructure / fault model).} All results
assume the trusted test infrastructure of \S\ref{sec:background}; an actor that also
mutates the oracle, checker, policy, CI, or compiler voids them. Workflow hashes
establish \emph{self-consistency}, not authenticity against such an actor.
\item \textbf{Correlated authorship and AI assistance.} Circuit, pseudo-oracle, tests,
and manuscript were produced within one project and substantially with AI assistance;
model agreement is not independent validation.
\item \textbf{Adaptive overfitting, partly mitigated.} The checker was hardened against
the same mutants later used as evidence. We added a \emph{pre-registered, out-of-sample}
corpus run once against the frozen checker (\S\ref{sec:heldout}); it is out-of-sample
but \emph{not} independent-adversary (same-project authorship), so we report
per-category outcomes rather than a mutation score.
\item \textbf{Pseudo-oracle pseudo-independence.} The oracle shares PLAS with the
circuit; a correlated spec misreading is possible. A cross-check against the project's
exact reference model is limited because that model implements a \emph{different}
(single-observer, stateless) functionality; we state the risk rather than claim it
eliminated.
\item \textbf{External validity.} ``Conformance'' means agreement with a pseudo-oracle
on tested inputs. Results are for one deterministic-query functionality, $N{=}3$,
$D{=}\{0,1,2\}$, one backend, and a single-host harness that is not an adversarially
isolated deployment; the backend-level observations were additionally checked on one
further MP-SPDZ version (v0.4.3), which is two versions, not a cross-version
compatibility claim. We do not imply an evaluated methodology across MPC applications
plural.
\item \textbf{No performance or simulation-security claim}; the boundary result is a
case-study observation, not a theorem.
\end{itemize}

\section{Related Work}
\label{sec:related}
Novelty statements below rest on a bounded, documented search; they are ``to the best of
a bounded search,'' not absolute (\S\ref{sec:threats}).

\paragraph{Test oracles and pseudo-oracles}
The oracle problem---deciding the expected result of a test---is surveyed by Barr et
al.~\cite{oracleproblem}; a pseudo-oracle (a second implementation of the same
specification) and metamorphic testing~\cite{metamorphic} are the standard responses
when no ground truth exists. Our anti-echo interface is a discipline for avoiding the
oracle-in-the-SUT trap in this setting; Wycheproof applies reference-oracle conformance
to crypto \emph{primitives} by feeding expected outputs, the opposite of our anti-echo
design.

\paragraph{Mutation testing and negative controls}
Mutation testing dates to DeMillo et al.~\cite{demillo1978} and is surveyed by Jia and
Harman~\cite{jiaharman}; whether mutants substitute for real faults is studied by Just
et al.~\cite{just2014}. We use mutants as an \emph{adequacy probe for a checker} and are
careful about mutant classes---killed, survived, stillborn (compile-invalid), and
benign/equivalent---never counting a stillborn mutant as a kill. Closest in spirit,
MASC~\cite{masc} evaluates crypto-misuse detectors with planted leaky mutants, but as an
offline third-party-detector benchmark rather than committed CI controls; and, unlike a
standard mutation-score study, we \emph{pre-register} a held-out corpus to counter the
adaptive coupling between a checker and the mutants used to harden it.

\paragraph{Leakage is dataflow, not opcode identity}
ct-verif reduces constant-time to a 2-safety property on LLVM~IR~\cite{ctverif};
Binsec/Rel decides constant-time \emph{relationally at the binary/opcode level} on
operand provenance, showing compiler backends inject leaks invisible to instruction-name
checks~\cite{binsecrel}; Securify decides EVM-bytecode security on inferred
\emph{dataflow} facts rather than syntactic patterns~\cite{securify}. Our \S\ref{sec:b6}
instantiates this principle in the MPC-application testing setting; we claim the
instantiation and the pinned-backend mechanism, not the principle.

\paragraph{Language-based security for MPC (the positive dual)}
Kerschbaum's information-flow type system certifies non-leakage of a mixed-protocol
secure computation at the \emph{source} level with a trusted compiler~\cite{kerschbaum}.
Closest to our finding, Skalka and Near give a \emph{sound} static security-type system
for a purpose-built low-level MPC IR, proving information is released only through
explicit declassifications~\cite{skalkanear,skalkanear2}. It is the positive dual of our
negative case-study observation: it is sound \emph{because} its IR makes declassification
syntactically distinct---the property MP-SPDZ bytecode lacks. Reproducible
Builds~\cite{reprobuilds} is the evidence-discipline neighbour; ours recomputes
per-case, oracle-bound test evidence rather than attesting whole artifacts.

\section{Conclusion}
\label{sec:conclusion}
On one MP-SPDZ application, a separately implemented pseudo-oracle, an anti-echo
interface, a strict transcript oracle, and recomputed evidence give real,
coverage-bounded, operationally-stated test assurance and kill a family of gross
delivery-fault classes---and they have a sharp, nameable adequacy boundary. A static
opcode-identity / channel-blocklist checker cannot be promoted to a general non-leakage
checker: a masked open and a raw reveal are the same instruction, and the register
channel a leak would use is the one the honest code uses. A pre-registered, held-out
mutation study makes the boundary concrete with a \emph{surviving} source-realizable
mutant (H-R2, a multiset-preserving mis-delivery) caught only by a downstream oracle.
Distinguishing the flows needs analysis stronger than opcode/channel identity---which we
did not evaluate---and a privacy guarantee needs a protocol-level proof. Naming that
boundary---and printing it next to the green check---is the case study's point.
